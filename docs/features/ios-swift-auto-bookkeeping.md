# iOS Swift 版：银行卡资金变动自动记账

选型见 [ADR 0008](../decisions/0008-ios-swift-shortcuts-app-intent.md)。代码：
`ios-swift/Bookkeeping/Intents/`（App Intent）→ `ios-swift/Packages/BKCore/Sources/BKBackend/`（解析与入账）→ `BKDatabase`（SQLite）。

## 闭环

```
资产页添加银行卡（银行、后四位、卡类型、币种或多币种，选填初始余额）
  → 「设置自动记账」→ 跳转快捷指令，用户新建一个自动化，用「信息」「电子邮件」「App 通知」触发（用「或」连接，立即运行），来源选「自动」，只需一次；
    「信息」条件不填；「电子邮件」至少要一个条件，填「主题包含」「你」；「App 通知」只选银行 App、不选「邮件」（邮件 App 的通知只有开头几行）
  → 银行短信 / 邮件到达 → 系统运行自动化 → 后台调用 App Intent「记录银行动账通知」（不打开 App）
  → BKBackend：归一化 → 用户识别模板 → 分类 → 解析 → 匹配账户 → 去重 → 同一事务入账 / 写待处理
  → 用户下次打开 App 时首页、卡片详情、统计刷新
```

## 输入协议（App Intent 参数）

| 参数 | 必填 | 说明 |
|---|---|---|
| 通知内容 | 否（缺失记为「空输入」日志） | 自动化里选「快捷指令输入」或其「内容」 |
| 来源 | 默认短信 | 短信 / 邮件 / 其他文本 |
| 发件人、主题、接收时间、消息标识 | 否 | 只有系统实际提供时才填；App 不用处理时间冒充接收时间，不编造消息 ID |
| 绑定账户 | 否 | `AccountEntity`；同尾号多卡时辅助匹配，正文尾号优先 |

返回值：一句处理摘要（例如「入账 1 笔」「待处理 1 条」），不弹任何对话框。

## 分类：哪些会记成交易

| 类别 | 处理 |
|---|---|
| 已发生的资金变动 | 入账（`status = posted`） |
| 支付失败 | 保留记录，`status = failed`，不计入收支和余额推算 |
| 预授权、冻结 | `status = hold`，不冒充已结算消费；预授权完成为 `posted`；撤销/解冻为 `holdReleased` |
| 验证码 | 只记日志，**不保存正文** |
| 营销、还款/账单/扣款提醒（含「将于…扣款」） | 只记日志 |
| 电子账单、对账单 | 只记日志，不把历史明细再入账一遍 |
| 只有余额 | 不入账、不保存余额，**不凭余额差额编造交易**；能对上卡时记为这张卡收到过自动输入 |
| 信用额度变化 | 只记日志，不是资金或负债变化 |
| 无法识别 | 进入待处理，不丢弃；可以用它做识别模板（见下） |

## 交易性质（不是用户分类）

消费、入账、工资、转入、转出、退款、还款、扣息、手续费、存入、取款、利息、冲正/撤销、其他（方向明确但性质不明）。
方向（流入 / 流出）相对账户本身：信用卡消费为流出、还款为流入。只写「还款」不写方向时，按账户卡类型决定。

## 解析规则要点

- **归一化**：HTML 转文本（`<blockquote>` 标为引用）、实体解码、全角转半角、去零宽字符。
- **邮件历史**：去掉 `>` 引用行和「Original Message / 原始邮件 / 写道」之后的内容；转发邮件取转发正文。
- **金额角色**：数字前最近的标签决定含义——余额、可用额度、手续费、累计、应还/最低还款、积分，其余为交易金额。
  同一句出现两个交易金额（例如「消费 100 实际扣款 95」）视为歧义，每个金额各进一条待处理；
  用户记入其中一条，同一条通知里的其他候选金额自动忽略（拆出的手续费保留）。
- **不是金额的数字**：电话号码（`+86-183******36`、`+852 3665 3665`）、打码的号码（`183******36`）、9 位以上的长数字、交易参考号；
  同一句已经有写明币种的金额时，没写币种、没有小数、后面紧跟着一个词的整数（商户「12306 beijing CN」里的 12306）。
- **中英双语**：同一笔写成中文、英文两段时只记一笔；英文那段认不出交易性质（其他）时以中文那段为准。
- **手续费**：「含手续费 X」→ 本金 = 总额 − X，另记一笔手续费；「转出 1000，手续费 2」→ 两笔，均不重复计算。
- **金额格式**：`1,234.56`、`1.234,56`、`12,50`、`1'234.50`；三位一组对两位小数币种是千位分隔；
  KWD 等三位小数币种的 `1.234` 视为歧义。全部转为最小货币单位整数。
- **币种**：以通知里写明的为准（人民币/元/¥/EUR/€/USD/HK$…）；`¥` 在中文通知里优先 CNY 但保留 JPY 候选；
  通知没写币种、或只写了「元」时使用账户主币种；写了 `¥`、`$` 等多义写法时优先取账户持有的币种（多币种账户据此区分）。
  **不根据手机地区推断**。都无法确定时进入待处理。
- **时间**：交易时间按通知原文保存为「墙上时间」（不做时区换算），只写月日时按接收时间推断年份并标记；
  `03/04` 这类无法区分日月的日期不写日期。交易时间与系统接收时间、App 处理时间分开保存。
- **尾号**：尾号/末四位/卡号**1234/账户1234/card ending 1234 等写法；「向尾号 XXXX 转账」中的是对方账户。
- **交易对方**：商户/对方户名/在…消费/…向您转账/转出至…/at MERCHANT 等写法；缺失为空，不编造。摘要字段只在不是通用词（消费、转账、工资…）时作为对方。

### 识别模板（用户在本机做）

通用读法认不准的写法，用户可以自己做模板（`UI/Pending/TemplateEditorView.swift`，和记一笔一样是弹出的表单）：在「我的 › 自动记账 › 识别模板」点右上角「+」，粘贴或手动输入一条短信 / 邮件；或者在「待处理」里点一条通知的「做成识别模板」。

1. 原文是整理过的正文（`MessageParser.cleaned`，和识别时看到的一样；粘贴的原文先整理再显示），用系统文字选择选中金额（必选）、尾号、对方，再和记账一样选支出 / 收入 / 转帐（支出可以标成退款，转帐选这张卡转出还是转入）。交易性质和方向由这几样推出来（`MessageTemplate.fields`），原来的性质还在同一类里就保留（手续费、工资、还款等）。粘贴后先用通用读法猜好金额位置和类型。
2. 模板只取选中内容所在的句子；前后文字（汉字、字母）少于 8 个时往前多取几句（例如邮件里金额单独一行），仍然太少就不让保存。
3. **去敏**：模板只保存写法——选中的位置换成占位，其他数字一律换成「任意数字」，不保存原文的任何数字；其余文字原样保留，用来认出同一种通知。
   模板只保存在这台 iPhone（`message_templates` 表），不发给任何人。
4. 识别时**模板优先于通用读法**（验证码除外）：文字一致（空白多少不限、不分大小写）、数字可以不同就算认出，
   用模板认出的那一笔代替通用读法的结果；时间和交易参考号仍由通用读法从正文里找。之后的匹配账户、去重、入账不变。
5. 保存时用新模板重新识别还没处理的待处理项：认得出的通知原来的待处理项关闭，按模板重新入账或换成新的待处理原因（例如还要选卡）；
   已经有流水入账的通知不动，避免重复记账。
6. 「我的 › 自动记账 › 识别模板」：点一个模板编辑（按原来的标识保存，`TemplateDAO.save`），往左滑或在编辑页里删除。
   模板里没有原文，编辑时用 `MessageTemplates.sample` 把写法还原成一条示例（金额 100.00、尾号 1234、对方「对方」、其他数字 0），圈好原来的位置；不改原文直接保存得到同样的写法。

代码：`BKModel/Templates.swift`、`BKBackend/Parsing/MessageTemplates.swift`、`IngestEngine.run` / `reapply`、`TemplateDAO`。

### 支持范围与样例依据

`Tests/BKBackendTests/ParserSampleTests.swift` 中的样例均为**按公开常见写法构造的脱敏文本**，覆盖：
招商、工商、中国银行等中文短信常见句式，英文银行卡短信 / 邮件，HTML 邮件、回复历史、转发、多笔交易邮件。
尚未用每家银行的真实通知逐一验证。用真实通知验证过的：恒生繁体短信、恒生转账邮件、恒生「無卡支付」邮件的 HTML 正文
（`Tests/BKBackendTests/HangSengEmailSamples.swift`，用户转发的真实邮件去掉转发人签名）。
识别不了的格式进入待处理；新增格式时在 `Lexicon.swift` 补词并补样例测试。

## 账户匹配

1. 正文尾号与账户后四位相同。解析前先把常见繁体字转成简体（「結尾號碼」→「结尾号码」）；
   按固定写法认不出尾号时，在正文里找已添加的卡的尾号（单独的 4 位数字，排除日期、金额和更长数字的一部分），
   只出现一张卡的尾号时就是这张卡（`IngestEngine.knownTail`）；
   通知只写账号（户口号码）时，和「卡片信息」里填写的账号、完整卡号比较，打码位 X / * / • 当作任意数字
   （`971-634XXX-888`，`IngestEngine.identifierTail`）。账号可以直接粘贴通知里打码的形式；
2. 同尾号多张卡时，用短信号码 / 邮件域名 / 正文【签名】识别的银行过滤；
3. 仍有多张时，若快捷指令绑定了其中一张，用它；否则进入待处理（`多个账户都可能匹配`），由用户在候选中确认；
4. 正文没有尾号：只有绑定账户时进入待处理（`通知里没有卡号尾号`），不直接入账；
5. 电子钱包发的、没写尾号的通知（见下）：记到那个钱包的账户；
6. 没有任何匹配账户：进入待处理；之后添加了该尾号的账户（或那个钱包的账户）会自动重新匹配。
   没有候选账户的待处理项可以在「待处理」里选任意一张使用中的卡或电子钱包记入。

### 电子钱包（支付宝、微信支付）

- 认不出银行时，按发件人（短信号码 95188、App 名称）和正文开头的署名（「【支付宝】」「微信支付」）认出是哪个钱包
  （`BKModel/Banks.swift` 的 `WalletDirectory`）。正文中间提到的「财付通」「支付宝」不算：银行短信常写「在财付通-美团消费」，那是银行卡的交易。
- 写了银行卡尾号的是用银行卡付的，照常按尾号记到卡上（银行自己的通知也会来，按重复处理）；在钱包通知里不再到处找像尾号的四位数字。
- 没写尾号的是钱包余额的收支：记到这个钱包的账户。一般只有一个，直接记；同一个钱包有几个账户（小号）时进待处理，让用户选。
- 钱包账户是哪个钱包：添加电子钱包时选；以前添加的没选，按名称猜（名称里有「支付宝」「微信」「零钱」等）。
- 认出是钱包、又认出了金额的通知不按「普通消息」过滤；没有金额的钱包通知（营销、提醒）照样过滤。

## 去重与事务

| 层级 | 规则 |
|---|---|
| 输入 | 指纹 = 来源 + （消息标识 或 归一化正文）+ 发件人 + 主题 + 系统接收时间。重复执行、并发多个自动化命中同一条通知 → 只处理一次（`UNIQUE` 约束） |
| 交易 | 有交易流水号/参考号 → 按账户 + 流水号；否则通知时间精确到分钟 → 按账户、方向、金额、币种、性质、状态、时间、余额 |
| 跨来源 | 短信与邮件特征完全一致 → 合并为同一笔的两份来源证据；只是金额相同、时间接近 → 待处理（`可能与已有流水重复`），由用户判断 |
| 同来源同特征 | 不会静默合并：进入待处理，可确认为另一笔真实交易 |

整个处理（指纹、记录、余额、待处理、转账关联）在一个 `BEGIN IMMEDIATE` 事务里，失败整体回滚。
**不会仅凭同金额、同商户、时间接近就删除第二笔交易**；所有合并都保留来源证据。

## 自动归类（分类）

见 [ADR 0014](../decisions/0014-ios-swift-entry-types-and-categories.md)。入账后在同一个事务里（`BKBackend/Categorizer.swift`），只归通知里写明了的，不猜：

- 转帐（自己的账户之间、还款、存取现金）不用分类；
- 手续费、扣息、工资、利息直接归到对应的分类；退款跟着原交易的分类；
- 其余都是待分类，在「待处理」里由用户选（不按交易对方记住分类，不按时间猜三餐；没确认对方的转账也不记住对方）。

## 内部转账、还款、退款

- 自己两张卡互转：两边流水都保留；金额相同、方向相反、30 分钟内且唯一匹配（或正文写明对方尾号是自己的卡）→ 同一转账组，不计入收支。
- 没配对到自己另一张卡的转账（转出 / 转入）：照常入账，先按转给别人统计（转出算支出、转入算收入），
  并放在「待处理 › 待分类」里：选「转给自己的账户」→ 算转帐，不计入收支，并记住这个对方；直接选分类 → 算转给别人。
  流水详情里可以随时改（`records.transfer_party`）。
- 信用卡还款：借记卡付出与信用卡收到都记为「还款」，不计入支出/收入；能配对时同组。信用卡上原有的消费才是支出。
- 退款 / 冲正：新记一笔流入，能唯一找到原交易时建立关联；原交易不覆盖、不删除。

## 余额

- **初始余额**：用户在添加卡或「卡片信息 › 编辑」里填写的「现在」的余额（可填欠款，即负数），每个币种一个。
- **推算余额**：从初始余额出发，加上之后到达的已入账流水；添加账户时没填余额的币种从 0 开始（2026-10-30 起）；更早添加、没填过的账户显示「未知」，不计入净资产，可在卡片信息里填校准余额。
  多币种账户每个币种分别推算，不做换算。流水用通知到达手机的时间和初始余额比较（通知内时间是银行所在地时间，和手机时区可能不同）。
- **卡里没有的币种的交易**（例如港币卡付人民币）：按主币种扣款，计入主币种余额。用户填了实际扣款就用它，否则按交易当天的汇率估算；
  还没有任何汇率时先不计入（[ADR 0013](../decisions/0013-ios-swift-record-editing-and-foreign-charges.md)）。
- **不使用银行通知里写的余额**（2026-10-26 起）：很多银行的通知不带余额，带的写法和含义也不统一（信用卡尤其如此）。
  解析器仍会认出余额字段并记在流水上（`balanceAfterMinor`），但不再保存余额快照，也不用它推算卡片余额。
  旧版本保存的余额快照（`balance_observations` 表）保留在数据库里，不再读取。

## 自动化状态（只展示可观测事实）

| 状态 | 含义 |
|---|---|
| 已提供 App 动作 | 随 App 安装，快捷指令可搜索 |
| 已导入快捷指令 / 已启用触发器 | iOS 不提供查询接口，App 无法得知，界面明确写「无法读取」 |
| 已验证 | 这张卡至少有一次真实输入成功处理，显示最近接收时间、来源和累计次数 |

## 记账结果通知

- 「我的 › 自动记账 › 记账结果通知」：全部 / 仅失败 / 关闭（默认关闭，第一次打开时请求通知权限）。
- 每笔交易一条本机通知（UserNotifications，不经过服务器）：
  - 成功：「尾号 1234 卡，消费，¥128.00，记账成功」；
  - 失败：「尾号 1234 卡，消费，128.00，记账失败：没有与尾号匹配的账户，已放入待处理」；
  - 整条无法识别：「收到一条无法识别的银行通知，已放入待处理」。
- 不发通知：同一笔交易的另一来源合并、重复输入、验证码、营销信息、只有余额的通知。通知不出声（银行短信本身已经响过）。
- 金额和尾号会显示在锁屏上；不想显示时在系统设置里把「显示预览」改成「解锁时」。
- 入账结果里的每一笔见 `IngestResult.items`（`BKModel/Ingest.swift`），通知文案在 `App/IngestNotifier.swift`。

## 隐私与数据保留

- 不联网（汇率由快捷指令导入，见 [ADR 0011](../decisions/0011-ios-swift-multi-currency-and-rates.md)）；日志只记录结果类别和计数，不记录正文、金额、发件人。
- 原始正文默认保留 30 天（可选 7 / 30 / 90），到期清空正文、保留指纹与流水；待处理项的正文保留到处理完成。验证码正文从不保存。
- 数据库文件保护等级 `completeUntilFirstUserAuthentication`：首次解锁后锁屏可后台写入；开机后从未解锁时入账失败并由快捷指令显示错误。

## 限制

- 只能处理系统实际交给 App 的内容；系统未投递、未触发的通知无法补回，不能保证银行发送了每一笔。
- 邮件自动化依赖 iPhone 自带「邮件」App 收到邮件；「电子邮件」触发**必须至少有一个条件**（用户 2026-10-30 在真机上确认，
  不加条件不能保存），条件只能按主题，也不能按发件人的显示名称（「Hang Seng」「ZA Bank」）。主题不一定写银行名
  （恒生转账「你已成功轉賬 Your transfer is successful Ref:[…]」、众安「你已收到CNY 14.05」「你已转出CNY 437.03」），
  但恒生、众安的动账邮件主题都有「你」，所以填「主题包含 你」。别的主题带「你」的邮件也会交给 App，App 认不出交易就不保存。
  内地银行多写「您」：有这样的银行，再加一个「主题包含 您」的电子邮件触发（或另建一个自动化）。
  触发后交给 App 的是整封邮件的 HTML 正文，App 去掉样式、标签和引用的旧邮件再识别。
  「App 通知」触发不要选「邮件」App：它的通知只带开头几行，长邮件的金额、尾号被截掉后 App 无法补回。
- 自动化必须由用户在快捷指令里手动创建；App 无法创建、导入或查询。除了「电子邮件」必须的主题条件，自动化不加条件，所有短信 / App 通知都交给 App：
  不按「银行」触发（繁体短信写「銀行」，外国银行是英文），也不按尾号（「信息包含」只能填一个词，要每张卡一个）。
  「电子邮件」也不按发件人筛选：银行会换发件地址（众安银行 2024-06-27 起改用 `notification@service.bank.za.group`、
  `notice@mail.bank.za.group`），恒生等多数银行不公布完整的发件地址清单；地址一换，自动化不再触发，漏记且没有任何提示。
- 由 App 判断是不是动账通知：没有任何尾号（固定写法认不出、正文里也没有已添加的卡的尾号或账号）、看不出是银行发的（没有【签名】、不是已知的银行号码 / 邮箱，正文里也没有「银行 / bank / 信用卡 / 扣账卡」等词）、
  也没有绑定账户、并且认不出完整交易（方向或性质不明）的，记为「不是动账通知」，**不保存、不写接收日志**（普通短信不会留在 App 里，朋友发的「转我100元」也不进待处理）。
- 发送方截断的通知（App 推送常见）：截掉的内容无法恢复；剩下的部分能完整认出交易时照常处理（找不到卡就进待处理），
  缺了日期、交易号码时只能按「同卡同金额 20 分钟内」判断和邮件是不是同一笔。
- 银行 App 的推送通知：新版快捷指令可以用「App 通知」触发（用户在真机上确认），可以只选银行 App。
- 一个自动化接收多种来源时「来源」选「自动」（`SourceKind.auto`）：App 分不出是短信、邮件还是 App 通知，
  所以把每条输入都当作可能来自另一渠道——关键信息一致（交易参考号，或分钟级时间 + 金额 + 余额）的合并为一笔，
  只是近似（同卡同金额 20 分钟内）的进待处理由用户确认。同一条内容重复送达仍由输入指纹去重。
- 免费签名约 7 天到期，到期期间自动化失败。
